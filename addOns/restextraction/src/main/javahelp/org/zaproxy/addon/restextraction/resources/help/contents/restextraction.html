REST Extraction

This add-on maps the interface of a REST API while you use ZAP as a proxy. You tell it which API to watch and what its endpoints look like, and it records every call that goes through ZAP: the HTTP method, the values in the URL, how often each endpoint was called, and the status code, headers and body of the response.

It only observes. Requests and responses are passed on unchanged and are never blocked.

The REST Extraction tab

The tab is next to History, Search, Alerts and Output. If you do not see it, click the green plus next to those tabs and select REST Extraction. The left side is for input and shows every API you added as a tree, with its endpoint patterns under it. The right side shows the calls and the documentation of what is selected in the tree. Drag the line between the two sides to make one of them wider. The help button at the top right, or F1, opens this page.

1. Add an API

Type the base URL of the API in Base URL of the API and click Add API, for example: 
https://jsonplaceholder.typicode.com
The base URL needs a scheme and a host. It may have a port and a base path, such as https://example.com:8443/api/v1, but no query (?) or fragment (#). http and https are different APIs. The host is not case sensitive, and https://example.com and https://example.com:443 are the same API.

2. Add endpoint patterns

Select the API in the tree, type a pattern in Endpoint pattern and click Add endpoint. A pattern is the path of an endpoint, relative to the base URL of the API. Write a part of the path that changes from call to call as a name in square brackets: 
/posts/[POST_ID]/comments
This pattern matches /posts/1223/comments and /posts/abcd/comments, and the report shows POST_ID = 1223 and POST_ID = abcd.

Rules for a pattern:

  • It starts with /. Type only the path, not the full URL.
  • [NAME] always stands for one whole part of the path. /files/[ID].json is not allowed.
  • A name has letters, digits and _ only, and is used once per pattern. Names are case sensitive: [id] and [ID] are different.
  • The path is case sensitive: /Posts is not /posts.
  • One / at the end is ignored, in the pattern and in the calls.
  • The query does not affect endpoint matching: /posts/1/comments?_limit=5 matches /posts/1/comments. Its query arguments are captured and can be verified.
  • Write a space in a fixed part as %20. Values are shown decoded, so /users/John%20Doe gives John Doe.
When a base URL or a pattern is not valid, or was added before, a message in red under the fields says why and nothing is added. The message goes away as soon as you change the text.

A call that fits two patterns, such as /posts/[POST_ID] and /posts/latest, is recorded under both.

3. Start and stop

Select the API (or one of its endpoints) and click Start. From then on every response that goes through the ZAP proxy and fits one of the patterns is recorded. The button now says Stop. Each API is started and stopped on its own, and the button always shows the state of the selected API. The tree shows for every API whether it is running and how many calls it recorded, for example https://jsonplaceholder.typicode.com (running, 12 calls), and for every endpoint its own number of calls.

Stop keeps what was recorded. Calls made before Start or after Stop are not recorded, and neither is traffic that is already in the History tab.

4. Read the calls and the documentation

Select an API in the tree to see all its calls, or one of its endpoints to see only the calls of that endpoint. The right side has two tabs, and both update while calls come in.

Calls shows one row per call: the time, the method, the status code, the endpoint and the value of every [NAME]. Redirects, client errors (4xx) and server errors (5xx) have their own colour. Click a column header to sort the calls by that column, and click it again to reverse the order. Above the table you can show only the calls of one method, for example only POST, and type a text to show only the calls that contain it in one of the columns, such as POST_ID = 1 or 404 (upper and lower case are the same). Next to it the number of calls is shown, for example 3 of 12 calls while a filter hides some. Select a row to see the response headers of that call below the table. Tick Full body to also see its response body there. A JSON body is indented; a body that is not complete JSON, like one that was cut, is shown as it was sent. A body longer than 64 KB (65 536 characters) is cut and ends with [cut off after 64 KB]. A body that is not text, such as an image, is shown as [binary, not shown].

Documentation is the readable documentation of the API:

  • the base URL of the API as the heading;
  • one section per endpoint pattern;
  • per endpoint the methods that were used and how often, for example GET: 3, POST: 1;
  • per variable the values it had and in how many calls, for example Values of POST_ID: 1 (3 calls), abcd (1 call);
  • per call the method, the status code, the value of every [NAME] and the response headers.
Lines longer than 100 characters are continued on the next line. The documentation shows no response bodies, so it stays fast with many calls; the body of a call is in the Calls tab.

Calls with any status code are recorded, also 404 and 500. Methods other than GET, POST, PUT, DELETE, PATCH, HEAD and OPTIONS are counted as OTHER.

5. Remove and clear

Select an API or an endpoint in the tree and click Remove, press the Delete key or right-click it and choose Remove. Removing an API removes its endpoints and recorded calls too, and its base URL can be added again afterwards. Clear calls forgets the recorded calls of the selected API, or of the selected endpoint only, and keeps the endpoints; a running API keeps recording. When recorded calls would be lost, the add-on asks first.

Good to know

  • The recorded data is kept while ZAP runs, also when you start a new ZAP session. It is gone when ZAP is closed.
  • For an HTTPS API the client has to trust the ZAP root certificate, as for all proxied HTTPS traffic.
  • When ZAP runs without a GUI (daemon mode) the add-on lets all traffic pass and records nothing, because APIs and patterns can only be added in this tab.

US11: define a specification

Select an endpoint and open Specification. An empty specification is neutral: calls are not checked. Choose an item kind (Method, Content type, Path variable, Query parameter, Body field or Header), fill its fields and click Add item. Non-Method items automatically add their method. The item list has Edit and Remove; rejected changes keep the previous specification. Removing or changing a method with dependent items asks for confirmation.

Types are String, Integer, Decimal and Base64. Integer and Decimal have optional inclusive minimum/maximum bounds. Text numbers use ASCII digits, without trimming; JSON kinds are checked strictly. Decimal comparisons are exact. Query/body/header items can be Required; wildcard body fields and path variables cannot. Body fields on any method are allowed, with a hint for GET, HEAD and DELETE. Field names include user.id, items[].id and scores{}. Concrete keys take precedence over map wildcards.

Content types are checked only when declared. Extra query/body fields are checked only after that location has at least one declared item; headers are never extra. A malformed body is reported without a cascade of missing/extra errors. CORS preflight requests stay neutral.

US11: inspect compliance

The tree shows green check and red cross counts when an endpoint has a specification. Calls has a Check column and an Only invalid filter, composable with method and text filters. Select a call for Request, Checks and Response details. Full body applies to both request and response details. Request headers are displayed in full. Warnings are symbolic and do not invalidate requests.

Documentation shows each endpoint specification, compliance counts, violation totals and the same diagnostics as call details. Captured request information is included; response bodies remain excluded. All traffic text is escaped. Editing a specification rejudges calls already recorded; clearing calls keeps the spec, while removing the endpoint removes it. Specs are session-only and are never inferred from traffic or saved between sessions.

US11: unmatched paths

Select a namespace and open Unmatched paths, also available from its context menu. Paths covered by that running namespace but matching no pattern are counted separately. They never change main tree counts, verdicts or documentation. Select a path and choose Add endpoint pattern to toggle literal/variable chips and edit variable names before normal pattern validation. Unsafe literal parts start as variables; root/empty paths cannot become patterns. Adding a pattern does not erase unmatched counts. Clear in this panel affects only unmatched data; clearing a namespace also clears its unmatched data.

Limits and safe local demonstration

Bodies are retained up to 64 KB; binary bodies are marked. At most 200 arguments and 10 levels of JSON are extracted, with warnings for skipped data. Numeric values are limited to 10,000 characters, decimal exponent magnitude to 9,999, unmatched paths to 1,000 distinct entries plus overflow calls. The proxy listener always observes and never blocks or modifies requests or responses.

The private prototype includes a loopback-only fixture and a step-by-step walkthrough in docs/demo-walkthrough.md. It runs on its own profile/install and proxy port 8091; it does not change ZAP_D, port 8080, browser proxy settings or certificate trust.
